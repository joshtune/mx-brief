Your AI Second Brain Is Slowly Rotting (Here's How to Fix It)

8.1K

Second brains decay — engineer staleness detection into memory.

If your agent memory files are append-only, you're accumulating contradictions that actively degrade agent output — and this is the maintenance layer nobody's guide covers.

details

What it is: A problem-first breakdown of *memory decay* in AI second brains — why append-only knowledge bases rot, and how to engineer detection + pruning instead of just adding more storage.

What Cole is doing different:

  • Everyone else's second-brain content stops at *architecture* (core docs + daily logs + knowledge graph). Cole starts where they stop: maintenance.
  • He's been running his own second brain for 6+ months — long enough that decay is observed, not theoretical.
  • Frames decay as an *engineering* problem with a designed solution, not a "just re-read your notes" discipline problem.

The standard second-brain shape (his framing):

  • Core behavior + memory docs — `memory.md`, `soul.md`, always loaded into context. Concise by necessity.
  • Daily logs — append-only running record of what you did.
  • Karpathy-style LLM wiki — knowledge graph of entities and concepts across your life/business.

Why it rots:

  • Duplicity is structural, not a bug. Core memory needs the concise version; the knowledge graph needs the detailed version. Same facts, two representations — they drift apart.
  • Contradictions are the actual killer. When the agent pulls a wiki doc that disagrees with `memory.md`, it doesn't error — it gets confused and produces worse output than having no memory at all.
  • Your life changes faster than your files. Stale entities/concepts get retrieved with full confidence. A memory that was true in January is now a lie the agent asserts.
  • Intra-graph drift too — two entities describing the same thing in different words, neither wrong, both incomplete.
  • Sources multiply the problem: conversations, email, calendar, client-call transcripts, inbound leads, project docs, codebases — dozens of inbound streams, zero outbound pruning.

The fix (his thesis):

  • Build stale-detection into the second brain itself — the system should flag contradictions and outdated entities, then update or delete them.
  • Treat it as a solved-by-design problem: he claims it's "quite easy to implement" once you stop treating the knowledge base as write-only.

Tools & links:

  • Hermes — open-source downloadable second brain, referenced as one of the "install in a couple hours" repos *(exact repo URL not stated in transcript — search "Hermes second brain GitHub")*
  • Open Claw — same category, open-source second-brain scaffold *(exact repo URL not stated in transcript)*
  • Granola — AI meeting notepad; sponsor, but relevant as a transcript source feeding a second brain
  • Archon — Cole's own agent-orchestration / harness-engineering project, the usual home for these patterns
  • Karpathy's LLM wiki pattern — entity/concept knowledge graph as agent-readable markdown

How mx-workflow should improve from this:

  • Your `CLAUDE.md` + `.claude/` context files are a second brain, and they're append-only right now. Same rot applies.
  • Add an `/mx:memory-audit` command — scan `CLAUDE.md`, context-primed files, and any memory docs for: (a) references to files/commands/ports that no longer exist, (b) two docs asserting different things about the same subsystem, (c) entries whose last-touched date is far behind the code they describe.
  • Timestamp every memory write. `/mx:context-prime` should stamp created/updated dates so staleness is computable, not vibes.
  • Make `/mx:context-clean` smarter than delete. Right now it removes context files; give it a *reconcile* mode that diffs the context file against current code and rewrites the drifted claims.
  • Contradiction check as a review gate. You already have `mx:hallucination-check` for invented APIs — the sibling is a *stale-context check*: does the guidance in CLAUDE.md still match the repo?
  • Single source of truth per fact. If a fact lives in both `CLAUDE.md` and a local context file, one should point at the other rather than restate it. Cole's duplicity problem is exactly what a plugin with layered context files invites.

Why it matters for you: You're building a workflow plugin whose entire value is persistent, reusable project context — and this video is the argument that context you never prune eventually makes the agent worse than a cold start.

The Creator of Claude Code Said to Do What Now?!

14.5K

Boris Cherny says delete your CLAUDE.md — Cole adds nuance

If you maintain a hand-built harness like mx-workflow, this is the argument for periodically ablating your own rules, skills, and hooks instead of accumulating them forever.

details

What it is: A reaction/analysis video unpacking Boris Cherny's (creator of Claude Code) Y Combinator interview claim that every six months you should delete your CLAUDE.md, skills, and hooks — and what he *actually* meant.

The claim that set it off:

  • Boris, verbatim: "every six months, delete your CLAUDE.md, delete your skills, delete your hooks, see what the model does, and it might surprise you."
  • He specifically calls out Opus 5: "for Opus 5, this is something we really do recommend" — the model may not need instructions you wrote for older models.
  • Supporting data point: Anthropic cut ~80% of Claude Code's own system prompt for Opus 5 and says it got *smarter*.

The nuance most people miss (the actual method):

  • Anthropic does not wipe and pray. They run ablation — a research technique Boris describes as "an eval, but you delete things to figure out the impact."
  • Process: delete the entire system prompt → add it back line by line → measure the impact of each individual line.
  • Direction matters: you start from nothing and add back only what the agent demonstrably needs. Most people do the opposite — start from what they have and try to trim.
  • Net effect: your AI layer becomes a set of lines that each earned their place, not sediment.

The second, more actionable point — altitude:

  • Boris's "really common mistake": overly specific instructions. "You must do one, then two, then three, then four."
  • For modern models that's the wrong shape. Instead:
  • Describe the task
  • Describe the guardrails
  • Describe the exit criteria
  • Then "let the model cook"
  • Ablation is just the mechanism for finding where you got too specific.

Where Cole pushes back:

  • Taking the tweet at face value reads as "your harness is obsolete, Opus 5 is too good for you" — that's a misread. Nobody at Anthropic is running zero-context.
  • The premise holds directionally (better models need fewer guardrails), but restriction cuts both ways: an over-constrained harness can hurt more than it helps, *and* deleting a rule that was actually load-bearing is a silent regression you won't notice for weeks.

Tools & links:

  • Claude Code — the harness under discussion
  • Y Combinator live event with Boris Cherny — the source interview, linked in the video description
  • No new repos or tools introduced in this one; it's a methodology video

How to apply this to mx-workflow:

  • You have ~50 slash commands, ~14 agents, and a stack of skills. That's exactly the kind of accumulated layer Boris is describing — and none of it has an eval attached.
  • Run a real ablation, not a purge: pick your highest-traffic commands (`/mx:review`, `/mx:build`, `/mx:commit`), strip their prompts to task + guardrails + exit criteria, run them on a fixed set of diffs, and add lines back only where output measurably degrades.
  • Audit for altitude: any command that reads "step 1, then step 2, then step 3" is a candidate. Rewrite as outcome + constraints. Your agent definitions (`mx-code-reviewer`, `mx-silent-failure-hunter`) are prime suspects — narrow lenses are fine, prescriptive procedures are not.
  • Build the eval harness first. This is the part the video hand-waves: you can't ablate without a measurement. A dozen frozen diffs with known-correct findings would give you the eval that makes deletion safe.
  • Cadence, not a one-off: tie an ablation pass to each major model release. Rules written for Sonnet 4 era models are dead weight on Opus 5.

Why it matters for you: mx-workflow is a large hand-built harness with no evals — this video is the case for treating every rule as a hypothesis you can delete and re-measure, which is the single highest-leverage change you could make to it.

  • Worked example: $100k net → $50/hr → $25/hr buyback rate. Pay someone $10/hr to do it, that's free money
