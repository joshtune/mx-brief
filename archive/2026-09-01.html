details

What it is: A rapid-fire walkthrough of 25 Grok Bot concepts split into 5 parts, using Nate's own live bot roster (Motion, Miner, Eyes, Studio, Views) as the working example.

How it works:

  • Concept 1 — A bot is one bot. Each Grok Bot has a name, a job title/label, and a description, and holds its own single ongoing conversation. Nate's `Motion` bot is labeled `animator` and its description is literally "creates motion graphics and animations for intros or transitions for YouTube videos" — the animations in the video itself came from that bot.
  • Concept 2 — Descriptions are the routing layer. This is the load-bearing idea: descriptions aren't documentation, they're how bots decide who to delegate to. `Miner` = "mines X for AI news, new models, new tools; also knows Nate's YouTube and X posts so the briefings stay useful for his content." `Eyes` = "a master at research, gathers lots of credible sources and helps form opinions based on facts and data." When bots collaborate later, the delegation decision is made purely off these strings. Vague description → bad routing.
  • Architecture takeaway — build an org chart, not a hub-and-spoke. The naive setup is you at the top talking to all 20 bots. Nate argues for a tiered structure: you talk to a small "C-suite" of executive bots; those executives know the bots on their teams, their strengths and weaknesses, and delegate down. Scales past the point where you can hold the whole roster in your head.
  • Concept 3 — Bot templates (the killer feature). Same pattern as n8n workflow templates or Claude skills, but for whole agents. A shared link opens the bot in your Grok Bot app, showing its instructions, memories, and skills before you import. Click add → it spins up and self-configures ("saving your memory and skill") with name, label, and description pre-populated.
  • Template caveat: credentials do *not* travel. A bot wired to someone else's ClickUp arrives unconnected — you re-auth to your own. You get the logic and prompts, not their accounts.
  • Publishing your own: open a bot → settings → Share as template. The bot generates a template of itself and returns a public link; anyone with the URL imports a clone into their ecosystem. Nate demos it end-to-end with his `Views` bot — copy link, paste into Google, import.
  • Concept 4 — Context vs. memory (two-parter). Context = everything the bot can currently see: conversation history plus whatever prompts and data you feed in. Memory = persisted state that survives across conversations. (Transcript cuts off mid-explanation of memory.)

The Hidden Flaw of EVERY Coding Agent Now Has a Solution

3.7K

Sponsored spot on Sonar's Hunter Agent for business-logic bugs

It's a 2-minute ad, but the framing — agents write code that's *correct and wrong* — is the exact gap your review agents in mx-workflow don't cover, and Hunter's playbook→hunt→prove→determinism loop is a pattern worth stealing.

details

What it is: A ~2-minute sponsored segment for Sonar's new Hunter Agent, wrapped in a genuinely useful thesis about why AI code review misses the bugs that actually hurt.

The thesis (the part worth your time):

  • Every existing scanner is built to find code that is wrong — syntactically broken or unsafe. SQL injection, XSS, path traversal. Pattern-matchable shapes.
  • But most agent failures aren't bad code. It's code that runs exactly as the agent intended and still isn't what the business needed.
  • The recurring offenders: access control, business logic, authentication/sessions — the rules the product runs on.
  • Key insight: *a business rule doesn't have a shape.* Code that violates a rule is syntactically indistinguishable from code that honors it. The only way to detect a violation is to already know what the rule was supposed to be.
  • Cole's field note: when companies he consults for get bad results from coding agents, it's "almost never the model's fault" — it's that their entire verification layer is aimed at the wrong class of defect.

How Hunter Agent works:

  • Not "let an agent rummage around the repo" and not a traditional LLM code review. It runs playbooks.
  • Three-phase loop: derive what the app is supposed to enforce → hunt for instances where it doesn't → prove each finding before surfacing it.
  • Deterministic: run it twice on the same code, get the same answer twice. Cole calls this out explicitly as the thing LLM-built apps normally can't do.
  • Findings land as regular issues in SonarQube Cloud — no new surface to learn.
  • GA now, Cloud Enterprise plan only.

Tools & links:

  • Sonar / SonarQube Cloud — static analysis platform; Hunter Agent surfaces findings as normal issues here
  • Hunter Agent — linked in the video description; no standalone repo (closed, commercial)
  • No open-source drop this time. Archon is untouched in this video.

What he's doing differently:

  • Shifting the review conversation from *vulnerability classes* to *intent classes*. The unit of review becomes "the rule this app enforces," not "the pattern this line matches."
  • Treating determinism as a product feature of an agent, achieved by constraining the agent to playbooks rather than free-roaming a repo.
  • Insisting on a proof step between detection and surfacing — the agent has to demonstrate the violation, not just claim it.

How mx-workflow can improve:

  • Your review fleet (`mx-code-reviewer`, `mx-silent-failure-hunter`, `mx-performance-auditor`, `mx-type-design-analyzer`) is entirely *shape-based* — each hunts a pattern. None of them knows what your app is supposed to enforce. That's the gap Cole is describing, and it's live in your repo.
  • Add a rules-extraction step: derive an explicit, checked-in list of business/access-control invariants (from the PRD in `/mx:prd`, from RLS policies emitted by `mx-schema-builder`) into something like `.mx/invariants.md`. That artifact is the missing input.
  • Then add an `mx-invariant-hunter` agent that takes those invariants as input and hunts for violations — the playbook model. Different from every agent you have now, because it's given the rule instead of inferring one.
  • Steal the prove-before-surface rule for `/mx:review` and `/mx:reject`: a finding without a concrete failure path (inputs → wrong state) gets dropped, not reported. Kills the noise that makes review agents ignorable.
  • Steal determinism as a bar: same diff twice → same findings twice. Worth testing on your existing agents; they almost certainly fail it today, and that's why `/mx:ratchet` is hard to trust.
  • Your `mx-schema-builder` already writes RLS policies — that's a machine-readable access-control spec sitting right there. Feeding it back in as review input is the cheapest version of this whole idea.

Why it matters for you: The pattern — extract the rules, hunt against them, prove each hit, stay deterministic — is portable to mx-workflow as a new agent class, and it plugs the one hole your entire review suite currently shares.

Watch This If Your Coding Agent is Ignoring Your Rules (You Need Hooks)

27.8K

Hooks turn agent guidance into deterministic guarantees.

Your mx-workflow leans hard on rules, agents, and slash commands — all probabilistic guidance — and Cole's argument is that the quality gates you care most about (validate, ratchet, check-ignores) should be hooks, not instructions the agent can skip.

details

What it is: Cole's most-requested video — a framework for when to move logic out of rules/skills and into hooks, the one primitive in a coding agent that's actually deterministic.

The core claim:

  • Hooks are "actions you guarantee are performed whenever we hit certain events" in the agent loop.
  • Everything else — CLAUDE.md rules, skills, sub-agent instructions — is *guidance*. LLMs are probabilistic; they interpret and drop steps, especially in large codebases with long checklists.
  • Hooks are the only layer that gives you a guarantee. That word is the whole video.
  • He's audited AI coding setups for hundreds of devs and entire companies: almost nobody uses enough hooks.

The five components of a coding harness (his taxonomy):

  • Rules — persistent guidance (CLAUDE.md / AGENTS.md)
  • Sub-agents — delegation
  • MCP servers — platform connections
  • Skills — reusable workflows and prompts
  • Hooks — deterministic automations ← the underused one

The canonical example he walks through:

  • Classic failure: your rules say "run the test suite and validate your work." Agent runs *part* of the suite, declares done, half your tests are still red.
  • Hook version: a Stop hook fires when the conversation ends → runs the full suite deterministically → on failure, forces the agent to resume and fix.
  • Same intent, but the agent no longer has to *remember* the order of operations.

The framework — when should a rule become a hook?

  • If it's phrased "when X happens, do Y" → that's event-shaped, make it a hook.
  • If it's a validation/audit/security check → hook, always. Don't ask the model to police itself.
  • If it's logging/observability → hook.
  • Goal: extract the process away from the agent so correctness doesn't depend on instruction-following.

Event surface he references:

  • Pre-tool (e.g. before a file read — block for security, audit access)
  • Post-tool
  • Stop / conversation-end (his favorite for validation gates)
  • Portable across harnesses: Claude Code, Codex, and Pi all support the hook primitive.

Supporting signal:

  • He ties this to Anthropic cutting the Claude Code system prompt by ~80% — the industry direction is *less* prompt-borne instruction, more structural enforcement.
