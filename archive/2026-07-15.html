Pydantic AI 2.0: The New Best Way to Build AI Agents is Composing Capabilities

21.2K

Pydantic AI 2.0 makes 'capabilities' the core agent primitive.

Cole reframes agent-building as composing reusable Lego-like bricks — a mental model you can steal for structuring mx-workflow's skills, hooks, and tools instead of piling them loosely onto agents.

details

What it is: A breakdown of Pydantic AI 2.0's new `capability` primitive — a self-contained unit bundling instructions, tools, lifecycle hooks, and model settings into one composable brick.

How it works:

  • A capability packages everything an agent responsibility needs: tools (its arm to the outside world), instructions, guardrails, lifecycle hooks, and model settings — in a single input to the agent definition.
  • An agent is now just a set of composable capabilities combined together, rather than an "unorganized pile of tools, instructions, and guardrails."
  • Capabilities are reusable across agents — piece them together like Lego blocks and share between your personal/business agents.
  • Think of capabilities as the layer above MCP servers: MCP packages tools for sharing; a capability wraps an MCP server *plus* the instructions, settings, hooks, and human-interaction/injection logic around it. MCP is a subset of what a capability holds.
  • Nothing underneath is new — hooks, skills, guardrails, sub-agents, MCP servers are things you already use (especially in coding assistants). The win is the *simplification* of pulling them into one framework primitive.
  • Positions Pydantic AI back in the lead after it fell behind the rise of coding-agent SDKs (Claude Agent SDK, Codex SDK), which are dead-simple for personal agents but slower and more token-heavy. Capabilities integrate cleanly with hooks, sub-agents, and MCP in just a couple lines.

What's different this time: Cole's angle is the *convergence* — the industry has been settling on the same components (hooks, guardrails, skills, MCP), and Pydantic AI 2.0 is the first to unify them under one composable abstraction instead of separate bolt-ons.

Tools & links:

  • Pydantic AI GitHub — source and 2.0 release notes

Why personal markdown agents break in production, and what replaces them.

If mx-workflow is ever meant to ship beyond your own machine, this maps exactly where a markdown/git second-brain stops working and what production memory + retrieval architecture you need instead.

details

What it is: A thought-leadership piece drawing the line between *personal* agents (markdown/Obsidian/Karpathy LLM wiki, git-backed, coding-agent-driven) and *production* agents shipped to many users — and arguing they must be architected completely differently.

The core split:

  • Personal agent — a coding agent (Claude Code, Codex, Hermes, Open Claw) manages an interconnected markdown knowledge base: index docs, tagging, categorization, entities, built up over time. Simple, flexible, fast, *yours*, all in git. Cole runs one daily.
  • Production agent — the moment you ship to other people, markdown collapses. You now need access control, governance, traceability/auditability, retrieval at scale, and live/multi-user data.

Why markdown doesn't scale (his argument):

  • Organization + search over a growing pile of files never scales — "there's a reason we have databases."
  • Cost: personal setups ride your Claude/Codex *subscription*, which is personal-use only — you can't run that in production. API-metered agents reading whole markdown docs are far too expensive at scale.
  • Retrieval over full-document reads can't be optimized enough to compete with proper indexed retrieval.

The production architecture he proposes:

  • A database as the scaling substrate, wrapped as a context layer for the agent (a wrapper over the DB).
  • Two responsibilities the DB/context layer must own:
  • Context retriever — scalable, cost-optimized retrieval (vs. dumping whole markdown files into context).
  • Agent memory — user memories + organized info the agent can retrieve well, preserving second-brain benefits.
  • Demoed on Redis as the platform, but he stresses the ideas apply to any production data store.
  • (Transcript cuts off mid-build — the concrete Redis implementation is the back half of the video, not captured here.)
