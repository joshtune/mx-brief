Anthropic Engineer Explains: What to Build Instead of AI Agents

292.3K

Build reusable Claude Code skills, not bespoke agents.

Nate distills Anthropic's own skill-building playbook into four concrete practices (saved scripts, progressive disclosure, etc.) you can apply to your Claude Code setup today.

details

What it is: A breakdown of why Anthropic's skills creators (Barry Zhang and Mahesh Murag) stopped building one-off agents and started packaging jobs as skills for one general-purpose agent, plus four practices that make skills actually work.

The core mental model:

  • Model = processor, agent runtime (Claude Code) = operating system, skills = apps
  • You don't rebuild the OS for every job; you give the same agent a skill containing the process, context, scripts, and examples for that specific task
  • Claude Code already reads files, writes code, and calls tools, so a skill just needs to steer it, not rebuild it

Practice 1: DRY for Claude (save proven scripts):

  • Anthropic's team watched Claude rewrite the same slide-styling Python script every run, burning tokens and producing inconsistent output
  • Fix: have Claude save the script inside the skill as a "tool for its future self" and execute that file on future runs
  • Nate's carousel workflow does this: renderers, templates, and scripts are fixed; Claude only changes the content
  • The prompt he uses: "Save the script you just used inside the skill's scripts folder. Update SKILL.md so future runs execute that file instead of rewriting it. Run the skill again and verify the result."
  • Still test it: run the same task twice, compare the important parts, confirm the skill is actually calling the saved file

Practice 2: Progressive disclosure (the mechanic's toolbox):

  • Claude doesn't load every skill's full instructions, examples, and scripts at startup
  • It starts with only the name and description of each skill, then loads the full body only when the job matches
  • Write skill names and descriptions so Claude can route correctly without reading everything (the transcript cuts off here; practices 3 and 4 are in the remainder of the video)

Tools & links:

  • Anthropic Agent Skills docs — official spec for SKILL.md, scripts folders, and progressive disclosure
  • anthropics/skills on GitHub — Anthropic's public skills repo with reference examples
  • Nate's free AI Automation Society community — where he shares his workflows and skill files

You Built Your AI Second Brain. Now What? (Here's How to Evolve It)

18.4K

Evolving a personal AI second brain into a shared team brain.

Cole lays out the architecture split (personal agent vs. centralized knowledge base) you'd need before any multi-user version of an agent system like mx-workflow makes sense.

details

What it is: Cole's follow-up to his year of "second brain" content — this time tackling what breaks when you try to make it a multi-user ("team brain") system instead of a personal one.

How it works:

  • His personal second brain currently saves him ~20 hrs/week (measured a few months ago); the graph view is just a nice-to-have visualization, not the practical part.
  • Going from personal → team brain isn't a rebuild — the key architectural call is to keep the personal agent layer separate from the shared knowledge base.
  • Each person keeps their own agent (personality + individual memory), but all agents pull from one centralized, permissioned knowledge store — distributed agents, centralized policy/knowledge.
  • Problems a team brain has to solve that a personal one doesn't:
  • Scale of ingestion — info pours in from many sources/collaborators; plain Obsidian + Markdown stops being viable.
  • Retrieval accuracy at scale — needs stronger retrieval strategies than a single-user vault.
  • Source citation — answers need to trace back to origin documents.
  • Security & permissioning — label documents at ingestion time by source, then enforce role/key-based access in the database so not everyone sees everything (Slack, GitHub, internal docs, etc. all need different access tiers).
  • Cole partnered with Oracle for this demo, using Oracle AI Database to handle ingestion, retrieval, and role-level permissioning at enterprise scale — but he frames the architecture as tool-agnostic; Oracle is just his pick for the demo.
  • He says he has a working example repo linked in the video description that you can hand directly to a coding agent to help you build this yourself (exact URL not present in the transcript excerpt — check the video description on YouTube).

Tools & links:

  • Oracle AI Database — used for ingestion, retrieval, and row-level permissioning in the demo
  • Working example repo — referenced as linked in the video description (grab the URL directly from the video page)

Why it matters for you: mx-workflow is currently built around a single operator's agent team — this video is basically the blueprint for the next step: separate a shared, permissioned knowledge/context layer (specs, past runs, decisions) from each agent's individual working memory, so multiple people or agent instances could plug into the same underlying project knowledge without stepping on each other's access or context.
