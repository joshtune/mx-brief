How to Actually Run Your Coding Agent Safely (And Avoid the Horror Stories)

13.5K

Sandbox your YOLO-mode coding agent with Docker.

If you run Claude Code with `--dangerously-skip-permissions` (you do), this shows the Docker sandbox setup that keeps a bad agent decision from wiping your filesystem, DB, or SSH keys.

details

What it is: A guide to running coding agents in full YOLO/auto-approve mode *safely* by isolating them inside Docker sandboxes instead of on your bare machine. Cole partnered with Docker on this one.

The core argument:

  • Every agent (Claude Code, Codex, Cursor) ships a skip-permissions mode — `claude --dangerously-skip-permissions`. You're using it daily.
  • The fix is NOT to stop using YOLO mode. Approving hundreds of actions kills autonomy and wastes your time.
  • The fix is to give the agent full autonomy inside an isolated environment where a mistake can't hurt the host.

The risks he enumerates (each maps to an isolation layer):

  • Filesystem — un-sandboxed agent can read/edit/delete any file or folder on your machine. Assume no real protection.
  • Processes & environment — it can kill processes, edit env vars, tear down apps. Common failure: agent hits a port conflict and kills your running apps to "fix" it.
  • Docker engine — needs its own engine so it manages its own containers, not destroying containers for your other running services.
  • Network — needs an allow-list of outbound URLs. Without it, a prompt-injection attack can grab an API key and exfiltrate it to an attacker's URL.

How the solution works:

  • Docker sandbox = isolated VM/container environment for the agent to work in.
  • Multiple graded levels of isolation (filesystem, process, own Docker engine, network allow-list) — Docker's docs lay these out as distinct tiers.
  • Chosen because it's free, easy to set up, and capable.
  • Real horror stories referenced: Claude Code / Cursor / Codex wiping databases and deleting directories.

Tools & links:

  • Docker Sandboxes — free isolated environments for running coding agents; the docs diagram drives the whole video's isolation model
  • Claude Code `--dangerously-skip-permissions` (YOLO mode) — the flag this whole video is about defanging

Why it matters for you: Your mx-workflow pipeline runs agents autonomously — before you point auto-approve agents at real repos/DBs, wrap them in a Docker sandbox with a network allow-list so a prompt injection or a bad `rm` can't touch the host; this is a concrete guardrail pattern to bake into the workflow.

Your OS Changes Everything for Local AI

5.3K

Windows vs WSL vs Linux for local LLM inference.

Same box, same chip, three OS choices — and one of them triples your prompt processing speed, which matters more than the hardware spec sheet when you're picking a Mac mini alternative.

details

What it is: A three-way OS shootout on the GEEKOM A9 Max (AMD mini PC, ships with Windows) running local LLMs — Windows native vs WSL vs bare-metal Linux.

The machine:

  • GEEKOM A9 Max — AMD-based mini PC, Windows out of the box. This is the Mac mini competitor in the room: same small-box form factor, but you get to choose the OS, which is the whole point of the video.
  • No pricing given in the transcript. Alex's usual framing puts these AMD mini PCs in the same rough bracket as a mid-spec Mac mini, but he doesn't do the dollar comparison here — this is purely a software-stack test.

The results (decode = token generation, prefill = prompt processing):

  • Windows + Ollama (default): worst case. Ollama on Windows runs 100% CPU, GPU completely idle. If you installed Ollama and thought "this chip is slow," this is why.
  • Windows + llama.cpp with Vulkan: beats default Ollama outright. This is the fix.
  • Windows + Lemonade: ties Vulkan on decode.
  • WSL: gives up roughly 1/6 of throughput vs Windows native. Acceptable tax if you want the Linux toolchain without dual-booting. Needs Kisak Mesa installed to be viable.
  • Bare-metal Linux: all three backends land within a few percent of each other on decode — so decode is basically a wash across every OS.
  • The one that matters — long prompt prefill: Linux with RADV (the Mesa AMD Vulkan driver) is ~3x faster than Windows. That's the benchmark that made him double-check his numbers.

The verdict:

  • Long-context work (RAG, big system prompts, code files pasted in) → bare-metal Linux + RADV, no contest.
  • Chat-only, short prompts → Windows is fine, just don't use stock Ollama.
  • Want Linux tooling without the reboot → WSL + Kisak Mesa, eat the ~17% throughput hit.

Tools & links:

  • llama.cpp — the inference engine doing the actual work; use the Vulkan backend on AMD
  • Ollama — convenient, but CPU-only on Windows for this chip
  • Lemonade — AMD's local LLM server stack, ties Vulkan on decode
  • RADV / Kisak Mesa — Mesa's AMD Vulkan driver; the Kisak PPA is what makes WSL usable
  • Gear links from the description: MSI EdgeXpert, ASUS GX10, 2-port 400Gbps switch, 4-port 400Gbps switch

Why it matters for you: If you're weighing a mini PC against a Mac mini for local AI, this is the hidden variable — the AMD box's headline numbers are an OS choice away from being 3x better or 3x worse, whereas a Mac mini gives you Metal-optimized inference with zero configuration.

The pricing lesson every founder should learn

details

What it is: A short clip breaking down how Boulton & Watt priced the steam engine in 1775 — and why it's still the smartest pricing model in business.

The featured business: Boulton & Watt, the partnership between engineer James Watt and manufacturer Matthew Boulton, selling an improved (far more coal-efficient) steam engine into British mines.

How they made money — the actual mechanics:

  • Zero upfront price. They gave the engine away free. No capex hurdle, no procurement fight, no "let me think about it."
  • Charged a third of the coal savings. Customer paid a recurring cut — one-third — of the money the new engine saved them on coal versus their old inefficient one.
  • Sold to installed base, not greenfield. They went to mines *already running* inefficient steam engines. The comparison baseline already existed, so savings were measurable and undeniable from day one.
  • Hardware as a service, 200 years early. The engine was a delivery mechanism for a metered savings contract, not a product sale.
  • Perfect incentive alignment. They only made money when the customer made money. No selling shelfware.
  • Geographic arbitrage on customer value. Coal cost more the farther a mine sat from a coalfield — remote tin mines paid the most. Those customers saved the most, so Boulton & Watt earned the most. The pricing model automatically routed early installs to the highest-value accounts.
  • Captured the upside instead of a flat fee. A fixed sale price would have left the entire savings surplus with the customer. The percentage take scaled with the value created.

The lineage:

  • Rolls-Royce "Power by the Hour" — airlines pay per hour the jet engine is in service, not per engine bought. Same model, ~175 years later.
  • Modern equivalents: usage-based SaaS, outcome-based AI pricing, performance-fee agencies.

  • Free HubSpot CRM — episode sponsor

The transferable playbook:

  • Find customers already paying a measurable, recurring cost.
  • Remove the purchase decision entirely (free to install).
  • Price as a percentage of the savings or revenue you generate.
  • Let the model self-select into the accounts where your value is highest.

Why it matters for you: If you ship anything that measurably reduces a cost or lifts a number, you can skip the pricing-page guessing game and just take a cut of the delta — the customers who benefit most will find you.
