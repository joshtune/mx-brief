I Love the Karpathy LLM Wiki but it Doesn't Scale. Here's What Does.

8.5K

Why personal markdown agents break in production, and what replaces them.

If mx-workflow is ever meant to ship beyond your own machine, this maps exactly where a markdown/git second-brain stops working and what production memory + retrieval architecture you need instead.

details

What it is: A thought-leadership piece drawing the line between *personal* agents (markdown/Obsidian/Karpathy LLM wiki, git-backed, coding-agent-driven) and *production* agents shipped to many users — and arguing they must be architected completely differently.

The core split:

  • Personal agent — a coding agent (Claude Code, Codex, Hermes, Open Claw) manages an interconnected markdown knowledge base: index docs, tagging, categorization, entities, built up over time. Simple, flexible, fast, *yours*, all in git. Cole runs one daily.
  • Production agent — the moment you ship to other people, markdown collapses. You now need access control, governance, traceability/auditability, retrieval at scale, and live/multi-user data.

Why markdown doesn't scale (his argument):

  • Organization + search over a growing pile of files never scales — "there's a reason we have databases."
  • Cost: personal setups ride your Claude/Codex *subscription*, which is personal-use only — you can't run that in production. API-metered agents reading whole markdown docs are far too expensive at scale.
  • Retrieval over full-document reads can't be optimized enough to compete with proper indexed retrieval.

The production architecture he proposes:

  • A database as the scaling substrate, wrapped as a context layer for the agent (a wrapper over the DB).
  • Two responsibilities the DB/context layer must own:
  • Context retriever — scalable, cost-optimized retrieval (vs. dumping whole markdown files into context).
  • Agent memory — user memories + organized info the agent can retrieve well, preserving second-brain benefits.
  • Demoed on Redis as the platform, but he stresses the ideas apply to any production data store.
  • (Transcript cuts off mid-build — the concrete Redis implementation is the back half of the video, not captured here.)

  • Claude Code / Codex — coding-agent SDKs powering personal second brains

Five levels of AI coding autonomy, mapped to self-driving.

Cole argues Level 3 (delegate-and-validate), not the fully autonomous 'dark factory,' is the sweet spot — a direct lens for tuning how much you trust your mx-workflow agents.

details

What it is: A breakdown of Dan Shapiro's five levels of AI coding autonomy, mapped onto the 2013 SAE five levels of driving automation — from 'spicy autocomplete' to the fully autonomous 'dark factory.'

How it works:

  • Level 0 — Spicy autocomplete: You write every line; the agent is a smarter Stack Overflow. Never has the final say.
  • Level 1 — Coding intern (cruise control): Agent writes boilerplate — repo setup, package installs, unit tests, simple refactors. Nothing that needs real reasoning.
  • Level 2 — Junior developer (highway autopilot): Heavy pair programming; agent runs autonomously in easy situations but you drive manually for anything with real rules/turns. Cole says most viewers are stuck here and should push past it.
  • Level 3 — Developer (where Cole operates): You build a real system for planning → implementing → validating, then delegate *all* coding to the agent. Cole hasn't written a line of code himself in over a year. Trust comes from the system, not blind faith.
  • Level 4/5 — Dark factory (full autonomy): Fully hands-off pipelines. Cole has built one himself but warns of significant downsides — powerful, but not where most should aim.
  • Key insight: The right level changes over time as your structured approach matures; most people self-assess higher than they actually are.

Tools & links:

  • Dan Shapiro's 'Five Levels from Spicy Autocomplete to the Dark Factory' blog post (source framework — search Dan Shapiro's blog; exact URL not given in transcript)
  • Referenced tools: Claude Code, OpenAI Codex
  • No specific repos linked in this transcript excerpt (thought-leadership piece, not a build walkthrough)

Why it matters for you: The plan→implement→validate loop is exactly what elevates mx-workflow from Level 2 (you babysitting each task) to Level 3 (agents own the code, you own the validation gates) — invest in the validation harness, not just more autonomy.
