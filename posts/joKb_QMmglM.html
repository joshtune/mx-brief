GPT-6 Astra Just Made AI Software Factories Real (Here's How to Run One)

Cole Medin · 2026-09-12 · 35,818 views  ·  Watch on YouTube →
Deploying a 24/7 autonomous PRD-to-shipped-code factory remotely.

Cole's 'dark factory' is the fully-autonomous endgame of what mx-workflow's /mx:build pipeline does interactively today, and this is his concrete setup recipe for running it unattended on a VPS.

What it is: A step-by-step guide to standing up Cole's open-source AI Software Factory (aka 'dark factory') on a remote VPS so it accepts PRDs or GitHub issues 24/7 and outputs validated, shipped code, with GPT-6 Astra as the driver model.

What he's doing differently now:

  • Model swap: After a week of head-to-head testing, he's putting GPT-6 Astra ahead of Fable 5.1 for autonomous coding. His claim: Astra needs far less intent clarification and makes fewer 'weird assumptions' than Opus 5 did. Benchmarks look tied; hands-on it wins 'a majority of the time'.
  • Harness over model: The factory is a full autonomous harness, not a prompt. PRD in, shipped code out, with validation loops in between. He says earlier this year this was unrealistic; the model jump is what made it viable.
  • Remote-first: He's moved from local testing to a persistent cloud instance. The vision is every dev and company running a factory that accepts input via GitHub issues at any time.
  • Agent-driven setup: Onboarding is a single prompt you paste into your coding agent. It interviews you for context, then builds the factory config for either a greenfield PRD or an existing codebase.
  • Dogfooding: He's using the factory on Archon and on video games he's building, and promises follow-ups on token efficiency.

How it works:

  • Clone the software factory repo (linked in his video description; his GitHub is https://github.com/coleam00).
  • Send the repo's bootstrap prompt to your coding agent. It runs an interview and scaffolds the harness.
  • Test locally first on a PRD or existing repo.
  • Deploy to a VPS (he uses Hostinger for the live demo; some steps are Hostinger-specific).
  • Wire an input channel like GitHub issues so the factory picks up work autonomously.
  • Output is validated code, not just a diff. Validation is part of the harness.

Caveats he's honest about:

  • Not AGI, not 100% reliable. He calls it 'close enough to be worth experimenting with', not production-grade for arbitrary code.
  • Token cost is a real concern; a dedicated efficiency video is coming.
  • Transcript cuts off during the Hostinger setup, so the actual deploy commands aren't captured here.

Why it matters for you: mx-workflow already has the pieces (prd → plan → implement → qa → shipit, plus quality-keeper as a gate); the gap is an unattended trigger and a remote runner, so the concrete lift is a `/mx:factory` entry point that takes a GitHub issue or PRD file, chains the existing commands headlessly, and runs on the Mac mini or a VPS via launchd/cron with mx-quality-keeper as the reject gate.
