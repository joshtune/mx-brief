DeepSeek Just Built the Next Generation of Coding Agents

Cole Medin · 2026-08-20 · 22,074 views  ·  Watch on YouTube →
DeepSeek's open-source, all-plugins coding agent harness.

Cole's thesis — that the winning harness is the one you can rip apart and rebuild plugin by plugin — is the exact design pressure to apply to mx-workflow's command/agent/skill sprawl.

What it is: DeepSeek open-sourced its own coding agent harness — 165k+ GitHub stars in under a week — where *every* component, including the agent loop itself, is a toggleable plugin.

What Cole is doing different here:

  • He's not evaluating it as a daily driver replacement. He explicitly says *don't* jump off Claude Code / Codex / Pi yet — it's "quite unrefined," "rough around the edges."
  • He's evaluating it as an architecture bet: the harness you can build on beats the harness that's better out of the box, on a long enough timeline.
  • His actual experiment (per the description): run DeepSeek's harness as the *orchestrator* and call Claude Code and Pi as subagents to do the real work. That's the interesting move — cheap/open harness on top, strong closed agents underneath as tools.

How the harness works:

  • Plugins all the way down. Not just "tools you add" — the UI, the inner workings of the harness, and the agent loop are themselves composable plugin units. You toggle each component on/off individually.
  • Plugin marketplace for installing third-party components.
  • Creator mode — a built-in mode that walks you through authoring a new plugin from a plain-English description of the functionality you want. The harness ships pre-wired to extend itself.
  • Model-agnostic by design. The explicit contrast with Claude Code and Codex: those lock you to a model set and give zero access to the internals.
  • Install: npm, or run from source. Cole took the easiest path (the README's quick-start) rather than building from source.

The thesis (this is the real content):

  • Self-evolving software is already realistic, so a coding agent evolving *itself* is realistic too.
  • But self-extension only works if there's an underlying framework that *standardizes* how a component gets added, enabled, and disabled — otherwise the agent has no safe grammar for modifying itself.
  • DeepSeek's plugin granularity *is* that grammar. That's why Cole calls this the shape of the future, not this specific tool.

Trade-offs Cole flags:

  • Rough, unrefined, early. Minimalism costs you the batteries-included ergonomics of Claude Code/Codex.
  • The middle path he keeps pointing at is Pi — self-extensible, but more finished than DeepSeek's harness.

Tools & links:

  • DeepSeek coding agent harness — the subject of the video; repo linked in the video description (transcript doesn't state the URL). Check github.com/deepseek-ai.
  • Pi — self-extensible minimal coding agent, motto "there are many coding agents out there, but this one is mine." Cole's long-running favorite and the closest prior art.
  • Claude Code / Codex — the "locked-in, no access to internals" foils.
  • Archon — Cole's own agent-orchestration/harness project, the lens he's judging this through.

Why it matters for mx-workflow:

  • Granularity is the lesson. mx-workflow is already plugin-shaped (skills, agents, commands) — the gap is that a user can't *toggle individual components off*. DeepSeek's move is per-component enable/disable, including the loop. Adding a config that switches individual mx agents/commands off per-project is the cheap version of this.
  • Steal creator mode. You have `/mx:create-command` already. Extend it to full self-extension: a mode that generates a new skill/agent from a description *and* registers it, so mx-workflow can grow itself the way Cole describes.
  • Harness-on-top pattern. His subagent experiment (open harness orchestrating Claude Code) is the same shape as mx's `/mx:build-with-agent-team` — worth watching whether cheap orchestration + strong subagents beats strong-everything on cost.
  • The standardized-extension point is the real takeaway: if you want mx-workflow agents to eventually modify mx-workflow, you need a documented, machine-readable contract for what a component *is* before that's safe.
