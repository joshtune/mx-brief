The Safest Way I've Found to Let AI Coding Agents Run Real Infrastructure

Cole Medin · 2026-09-08 · 2,333 views  ·  Watch on YouTube →
Sandbox coding agents behind Kestra YAML workflows, not credentials.

Cole's permission model here (agent invokes named workflows, never touches secrets) is a directly liftable pattern for how mx-workflow's build/ship/deploy commands should expose infra actions to Claude.

What it is: A sponsored Kestra 2.0 walkthrough where Cole shows how he lets coding agents touch real infrastructure without ever handing them cloud keys, DB URLs, or raw shell.

What Cole is doing differently now:

  • Still writes every line with coding agents, still validates everything by hand. His trust ceiling isn't the model, it's the blast radius of what the agent can reach.
  • Stops giving agents raw credentials. Instead, an orchestrator wraps the agent and exposes a fixed list of workflows it's allowed to invoke.
  • Credentials live inside the orchestrator's workflow definitions, never in the agent's context or env.
  • Example agent in the demo can only restart services and scale replicas. Nothing else. That allowlist IS the whole permission model.

How it works:

  • Agents and operations are defined as YAML files committed to Git alongside the agent config.
  • Each agent gets a declared set of callable flows; anything outside that list simply doesn't exist from the agent's point of view.
  • Every agent call becomes a normal Kestra execution with inputs, logs, and results visible in the dashboard, so unattended runs stay observable.
  • Kestra 2.0 is out; the AI agent piece ships in the Apache 2.0 open-source core, not gated behind enterprise.

Tools & links:

  • Kestra — open-source orchestration platform; workflows-as-YAML in Git, now with a first-class agent layer
  • Kestra on GitHub — Apache 2.0 core
  • Kestra docs — flow/YAML reference for defining the allowlisted operations

Why it matters for you:

  • mx-workflow currently lets `/mx:shipit`, `/mx:release`, and `/mx:build` run git push, deploys, and Supabase schema changes with whatever creds are in the shell. That's exactly the exposure Cole is closing.
  • Concrete lift: define infra actions (deploy, migrate, restart, publish) as named workflows with creds injected at execution time, and have the mx commands call those by name rather than executing raw commands. Kestra is one option; the pattern also works with a thin local runner.
  • Second lift: per-command allowlists. `/mx:qa` shouldn't be able to reach anything `/mx:release` can. Right now they share one permission surface.
  • Third lift: every agent-triggered infra action should leave an execution record (inputs, logs, result) you can audit after the fact. mx has agents run unattended; it doesn't yet have that ledger.

Caveats:

  • Sponsored, short, demo-only. No real migration story shown, no failure cases, no discussion of how the agent discovers flows or handles a denied call.
  • Kestra is a JVM service you'd need to run on the mini; weigh that against a simpler allowlisted-script approach before adopting wholesale.
