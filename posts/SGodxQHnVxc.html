No One Talks Enough About Security for AI Coding. Here's How I Do It in My Workflows

Cole Medin · 2026-09-10 · 6,527 views  ·  Watch on YouTube →
Deterministic security gates for AI-generated code via Archon + SonarQube.

Cole's shifted from 'agent reviews agent' to hard-coded scanner gates inside Archon workflows, which is exactly the pattern mx-workflow's review/QA stage is missing.

What it is: Cole's argument that AI coding agents ship insecure code more often than they ship slow or undocumented code, and his fix: deterministic vulnerability gates (SonarQube) wired into Archon workflows so nothing reaches a PR without a scan.

What he's doing differently now:

  • Runs *every* coding workflow through Archon as the engine. Each process (plan, build, verify, ship) is one file of stitched nodes: agents plus scripts, executable in parallel.
  • Security is a deterministic node, not another Claude call. He explicitly rejects the 'obvious' fix of a second agent doing a security review as the primary control.
  • The gate runs *before* a PR opens or control returns to him. The agent must detect *and* iterate on findings, not just report them.
  • Partnered with Sonar, so expect SonarQube to be his default scanner going forward.

How the vulnerabilities get in (his taxonomy):

  • Direct code vulns — agent writes the SQL injection itself.
  • Dependency vulns — agent installs a package (or version) with a known CVE without checking.
  • Transitive vulns — the package is clean but a sub-dependency carries a CVE. Agents research the top level at best, never the chain.
  • CVE list is massive — no agent is going to reason over it from context. It has to be a tool lookup.

How the workflow works:

  • Archon node graph: coding agent → SonarQube scan (SAST + dependency/CVE check) → agent reads findings → fix loop → gate passes → PR opens.
  • Determinism comes from scripts, not prompts. The scanner either passes or it doesn't.
  • Agent still does all the work; the harness just refuses to hand back control until the gate is green.

Tools & links:

  • Archon — Cole's open-source harness builder; packages agent + script processes into single executable workflow files.
  • SonarQube — SAST + dependency vulnerability detection; his deterministic gate. (Sponsor, disclosed.)
  • CVE database — the list he says agents can't reason over without tooling.

Why it matters for you:

  • mx-workflow already has `/mx:deps` and `/mx:review` with 8 review agents, but those are agent-as-reviewer, the pattern Cole says isn't sufficient on its own. Add a deterministic scanner node.
  • Concrete moves for mx-workflow:
  • Wire `/mx:deps` into `/mx:ratchet` or `/mx:reject` as a hard gate: fail the verdict on any known CVE, including transitive, rather than reporting it.
  • Add a `security-scan` step to `/mx:build` and `/mx:pr` that runs a real tool (`pnpm audit`/`osv-scanner`/Semgrep/SonarQube) and feeds findings back to the implementing agent as a fix loop, not a report.
  • Give `mx-quality-keeper` a scanner it can invoke, so the QA gate has a deterministic input and isn't purely another Claude opinion.
  • Consider the Archon 'one file per process' shape: mx-workflow's commands are already close, but they don't yet stitch script nodes and agent nodes into one executable graph.
  • Net: Cole's thesis is 'agents build, scripts verify.' mx-workflow verifies with agents. That's the gap.
