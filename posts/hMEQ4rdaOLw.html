11 quick AI-layer fixes for annoying coding agent behavior

Each fix is a concrete tweak to skills, rules, or hooks, which maps directly onto improving your mx-workflow skills, especially the reviewer/QA ones.

What it is: A rapid-fire sequel covering 11 common coding agent annoyances (false 'done' claims, tests passing while the app is broken, ignored rules, burned usage limits, etc.), each with a small fix applied to your skills, rules, and hooks.

How it works:

  • Framing: Cole says engineers are now "engineers of the harness". The work is tuning your AI layer (skills, rules, hooks) so the agent succeeds in your codebase.
  • Repeatable method for every tip: (1) describe the problem to your agent, (2) discuss what in your skills/rules/hooks could change, (3) let it propose edits, (4) co-author them with the agent. He insists the fix has to be custom to you, not just a generic framework default.
  • Problem #1, agent says it's done when it isn't: Play devil's advocate.
  • Quick version: in the same conversation, ask "What would make this not actually work? What are the gaps between what the issue asked for and what you did?"
  • Agents are good at finding gaps when asked, but the list will be exhaustive and people-pleasing. Skim for the 2-3 items that jump out, don't fix everything.
  • Formal version: a separate reviewer skill handed to a different agent (fresh eyes). It critiques the work and can send gaps back to the builder.
  • Many frameworks ship this reviewer pattern, but a reviewer tuned to your project's failure modes beats the generic one.
  • Other problems named in the description: tests that pass while the app is still broken, ignored rules, burning through limits. The transcript excerpt cuts off before these, so the specific fixes aren't covered here.
  • Format: One chapter per tip, so you can jump to the ones you care about.

What he's doing differently now:

  • Treats skills, rules, and hooks as the main product of engineering work, not the code itself.
  • Uses the agent to help design its own guardrails, instead of hand-writing them.
  • Splits builder and reviewer into separate agents with separate skills.

How mx-workflow can improve:

  • Adversarial 'gaps' pass: Add a step to `/mx:implement` or `/mx:shipit` that asks "what would make this not work, and what's the gap vs. the ticket/PRD?" before declaring done.
  • Reviewer as a separate agent: You already have `mx:mx-code-reviewer`, `mx:reject`, and `mx:quality-keeper`. Check that they run in a fresh context against the original spec (not the builder's summary) and can route gaps back to the builder.
  • Make reviewers project-specific: Feed them per-repo failure modes from CLAUDE.md instead of keeping them fully generic.
  • Self-tuning loop: Add a skill that takes a described agent annoyance and drafts proposed edits to skills, rules, and hooks for you to approve.
  • Watch for the rest: Tips on tests passing while the app is broken, ignored rules, and usage limits likely map to `/mx:e2e`, hooks that enforce CLAUDE.md, and token cost. Watch the full video for those, since the transcript was truncated.

Why it matters for you: The reviewer-as-separate-agent pattern and the 'tune the harness with the agent' loop are two cheap upgrades you can make to mx-workflow this week.
