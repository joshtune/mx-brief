Your Coding Agent Has a MASSIVE Blind Spot (You Need to Fix It)

Cole Medin · 2026-11-12 · 1,227 views  ·  Watch on YouTube →
Give coding agents live production telemetry, not just code

Short sponsored pitch, but the underlying idea (agents verifying runtime behavior, not just reading source) is a real gap you can close in your mx-workflow skills.

What it is: A Dynatrace-sponsored ~2 min pitch arguing coding agents are blind to runtime behavior, so you should wire production observability into them. Light on detail, heavy on the sponsor.

How it works:

  • The failure story: Cole shipped a new version of his email-drafting agent (part of his AI second brain). It passed evals, then on its first production run it saw two unanswered emails, made zero tool calls, and reported nothing needed attention.
  • Why nobody caught it: no crash, no error, and nothing in the codebase made the bug obvious. He only found it by watching the actual run. Fix took ~7 minutes once seen.
  • The thesis: the agent sees the whole codebase but not what the code does once running.
  • The Dynatrace demo: an app with ~89 second response times. The agent is asked for the top 5 methods hitting the database hardest and gets a ranking from real telemetry.
  • Code + telemetry join: because the same agent can read source, it traces the worst offender to an exact line, a search query doing a full table scan on every call.
  • The fix: add a database index, with zero application code changes. Reading the code alone, it looked like a normal query. Only the numbers showed where CPU was going.
  • Takeaway: whatever tool you use, give the agent a way to see runtime behavior.

Tools & links:

  • Dynatrace MCP Server — streams production telemetry into the agent in your IDE. Cole says the link is in the video description; no URL is given in the transcript, so grab it there.
  • MCP (Model Context Protocol) — the transport that connects the agent to the observability data.
  • No repos mentioned. Archon and his second-brain agent are referenced only in passing or by implication, with no links.

What he does differently:

  • Treats runtime observability as a first-class input to the coding agent, not just a human dashboard.
  • His own lesson is that evals passing is not the same as production working. The real check was watching a live run.

Why it matters for you (mx-workflow):

  • Add a post-deploy verify step. After `/mx:ship` or `/mx:implement`, have the agent inspect logs, traces or a real run output, not just lint, type-check and tests from `/mx:validate`.
  • Hunt silent no-ops. His bug was an agent that did nothing and reported success. Extend `mx:silent-failure-hunter` or `mx:hallucination-check` with a check like: did the agent make the tool calls it should have, and does the output claim match the trace?
  • Feed `mx:performance-auditor` real data. It is static-analysis only today. Optionally let it consume telemetry (Dynatrace MCP or any APM or log MCP) to rank hotspots by measured cost rather than guesswork.
  • Caveat: this is a sponsored segment with no repo and no walkthrough. Treat it as a prompt to design the hook, not a recipe to copy.
