When Fable 5.2 beats Opus 5.5, and when it doesn't

Cole's core idea is to spend Fable only on hard, open-ended decisions and use Opus for the rest, which maps straight onto how mx-workflow should route models across skills and agents.

What it is: A guide to Claude Fable 5.2: where it justifies roughly 2x the Opus 5.5 price, plus effort levels and prompting. The transcript we got cuts off before the effort-level and prompting sections, so those are only previewed here.

How it works:

  • The model split: Fable 5.2 is the smartest model in Claude Code right now, and also the fastest way to burn rate limits. It is about 2x Opus 5.5's price. Cole says to be strategic, not to use it for everything.
  • Where Fable wins: big, complex decisions (e.g. application architecture) and really open-ended tasks. Cole says it blows other LLMs out of the water here.
  • Where it doesn't: simple or well-defined tasks. Cole says Anthropic's own resources note there's no real advantage to the bigger model on these, so Opus 5.5 is good enough.
  • His escalation workflow (the new trick):
  • Work through a hard design decision with Opus 5.5 until you hit the usual wall: decent answers with holes, or Opus asking you questions and never fully satisfying you.
  • Take that whole conversation transcript and hand it to Fable with the problem statement and how you've been ideating.
  • Fable comes back with what he calls a near-perfect solution in about 10 minutes.
  • Cost data (Artificial Analysis):
  • Fable at Max reasoning averaged about $26.54 per task. Opus 5.5 at Max is less than half that.
  • Fable at High is about $9 per task. Opus at High is about $3.46. The transcript garbles this figure, so treat it as approximate.
  • Cole's takeaway: Fable is not more token-efficient than Opus. Per-task cost is often *more* than double, so the premium doesn't pay for itself through efficiency.
  • The 'self-aware' demo: told not to reply to a message, Fable 5.2 returns thinking tokens but an empty response. Older models always emit tokens. Cole's point is that it's better at breaking out of default LLM behaviors.

What to steal for mx-workflow:

  • Add an explicit escalation skill. Something like `/mx:escalate` that bundles the current session transcript plus a problem statement and hands it to Fable for architecture or ambiguity calls. It's Cole's Opus-stalls-then-Fable pattern, productized.
  • Route models by task type. `/mx:prd` and `/mx:plan` are open-ended, so they're candidates for Fable. `/mx:implement`, `/mx:commit` and `/mx:validate` are well-defined, so Opus. Make this a documented default in each skill or agent frontmatter.
  • Set the model per agent. `mx:mx-feature-builder` and `mx:mx-quality-keeper` are mostly well-specified work, so keep them on Opus with a moderate effort. Reserve Fable for a planning or architecture agent.
  • Add a cost guardrail. Per-task cost matters here: Fable at High is about $9 vs about $3.46 for Opus. Have `/mx:build` and `/mx:loop` report which model ran each phase so runaway spend is visible.
  • Re-check prompt scaffolding. Fable seems to follow 'do nothing' style instructions. Once Cole's prompting section is out, audit skills for over-explained hand-holding that Fable no longer needs.

Why it matters for you: The takeaway for mx-workflow is model routing: Opus by default, and a deliberate hand-off to Fable only where open-ended judgment is the bottleneck.
