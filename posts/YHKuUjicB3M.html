My AI Software Factory Ships Hundreds of PRs a Week (Here's How I Manage It)

Cole Medin · 2026-11-02 · 25,211 views  ·  Watch on YouTube →
Mission-control dashboard for an autonomous AI software factory

Cole walked back his fully autonomous 'dark factory' to a human-in-the-loop design with a control plane, which is the pattern to steal if you want mx-workflow to scale past one-off runs.

What it is: A dev-log tour of the mission-control dashboard Cole built to run his AI software factory, which takes any issue or whole release, plans it, and builds it in an autonomous loop.

How it works:

  • Dark factory is dead. Early 2026 version: PRD in, split into issues, per-issue verification and code review, merged straight to prod with zero humans. Fine for proofs of concept, not reliable enough for real work. He renamed it the *software factory* after adding humans back in.
  • Minimal-decision principle. Goal is the smallest set of human decisions that gives the most control. The factory runs autonomously and bubbles up only the high-level calls that need a person.
  • Dashboard views mentioned:
  • At-a-glance map of the whole workflow, down to every individual skill run through the agents
  • Log of key decisions made while evolving the factory
  • Per-factory run history ('laps'). Two factories are wired in so far
  • Decision queue for items the factory escalates to the human
  • Why a control plane. He first resisted it, expecting less autonomy and more management. It turned out to be the only way to track dependency mapping, parallel execution, per-app validation setup, staging environments, and every human-in-the-loop point. Decisions used to live in GitHub issues and now bubble up in one view.
  • Factory as a living system. Even a reliable build needs constant evolution as process and product change. He says every company building factories at scale ends up with a dashboard like this.
  • Caveat: The transcript cuts off early, so the deeper walkthrough (specific skills, verification steps, staging setup) is not covered here. Watch the video for the actual UI tour.

Why it matters for you: For mx-workflow, steal three ideas:

  • Add an explicit decision-escalation step where skills surface only the human calls that matter, instead of burying them in issue threads
  • Build a visibility layer showing the skill graph and past runs, so you can see which skills to evolve
  • Log key decisions about why a skill changed, so the workflow improves deliberately instead of drifting
