How to Build the Most Powerful System for AI Coding (Full Breakdown)

Cole Medin · 2026-08-14 · 21,143 views  ·  Watch on YouTube →
Building an autonomous 'AI dark factory' repo that ships itself.

Cole packages months of harness engineering into a single Claude skill that turns a PRD into a self-planning, self-building, self-reviewing repo — which is exactly the layer your mx-workflow command/agent suite is one step below.

What it is: A "dark factory" — a repo where you submit a spec and shipped, reviewed, validated code comes out the other end, with zero human in the planning or validation loop. Cole distributes it as a Claude skill that scaffolds the whole harness from your PRD.

The framing — Dan Shapiro's 5 levels of AI coding (car analogy):

  • L0 — stick shift: you write the code, AI is "spicy autocomplete"
  • L1–L2 — pair programmer: AI writes boilerplate, you drive
  • L3 — hands off the wheel: agent writes most of the code, but *you* still do planning + validation. Cole says this is where most engineers are and mostly *should* be — most reliable, but you are the bottleneck
  • L4–L5 — dark factory: no steering wheel. You can't shape individual plans or validation strategies. Only a console for high-level direction (the PRD). You specify the destination; the agent does the rest

How the harness actually works:

  • Front-load the engineering, not the vibes. Cole is emphatic: this is *not* vibe coding. You trust the agent with the codebase precisely *because* you spent heavy effort building the harness first
  • Planning agent — the spec is decomposed into a real plan before any code is written; plan quality is the whole game at L4+
  • Adversarial critique loop — a *separate* agent critiques the primary builder's work. This is the load-bearing piece: the reviewer must be a different agent than the implementer
  • Validation gate — code doesn't ship until it's been reviewed and validated inside the factory, since you're not there to do it
  • The skill encodes the lessons, not the code — millions of tokens and months of iteration compressed into best-practice scaffolding, so you inherit the harness design instead of rediscovering it

Proof of work — the app he built without reading a line of shipped code:

  • Agentic chat app that does RAG over his entire YouTube channel, with source citations
  • For Dynamis community members it also searches course + workshop content
  • Not the most complex app, he admits — but it proved a human can be fully out of the loop

The timing argument (why now):

  • Three things compounding simultaneously: the models (Opus 5, Fable 5, new GPT and Grok models), the coding agents, and the harnesses we build around them
  • Honest caveat, stated repeatedly: not reliable for everything, not production-grade for every codebase. "A window into the future," not a finished product
  • His advice: don't jump straight to L4. Earn it at L3 first

Why it matters for you: mx-workflow already has the parts of a dark factory scattered across commands — `/mx:prd` → `/mx:plan` → `/mx:implement` → `/mx:qa` → `/mx:review` with a real adversarial reviewer bench (mx-code-reviewer, mx-silent-failure-hunter, mx-quality-keeper) — what you're missing is Cole's move of fusing them into one unattended loop with a machine-readable pass/fail gate; you already have `/mx:reject` and `/mx:ratchet` emitting verdicts, so the highest-leverage next step is a `/mx:factory` that takes a PRD and runs prd→plan→build→critique→ratchet in a closed loop, re-entering implement on reject instead of returning to you.
